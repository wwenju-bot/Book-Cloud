### 2.1 架构版本化与 diff ✅ 已完成

1. 架构解析/优化/人工编辑均新增版本而不是覆盖（`novel_architecture_version.version_no` 递增），`01-全局架构/v{n}-架构.md` 每版本独立文件，`当前架构.md` 始终指向最新审核通过版本。

2. `novel_review_record` 表落地，记录每次审核的操作人、意见、时间，供后续追溯。
3. `POST /chapter/version/{id}/review` + 架构审核写记录；菜单权限见 `sql/book_novel_menu_20260807.sql`。

### 2.4 异步任务 + 进度推送（SSE） ✅ 已完成（前端默认轮询）

1. 建表 `novel_generation_task`，新增 `TaskExecutorConfig`（自定义线程池：核心线程数、队列长度走 Nacos 配置）。
2. 把阶段1里同步调用的架构解析/优化、章节生成，统一改造成：接口收到请求 → 插入 `pending` 任务 → `taskExecutor.execute()` 异步跑实际逻辑并更新 `status`/`progress` → 立即返回 `taskId`。
3. `GET /task/{id}`：查询任务当前状态/进度（供前端轮询兜底）。
4. `GET /task/{id}/stream`：SSE 长连接推送进度（`text/event-stream`，用 Spring 的 `SseEmitter`）；工作台现阶段用轮询。
5. 任务失败要写清 `error_msg`（区分"模型调用超时"“模型返回内容不合规"“内部异常"等类型，便于前端展示友好提示）。

### 2.5 知识库模板补全与导出优化 ✅ 已完成

1. `KbOperationLogger` 追加写入 `05-操作日志/{yyyyMMdd}.md`（生成/审核/导出/转正等）。
2. `GET /project/{id}/export?approvedOnly=true`：跳过 `03-章节优化记录` 草稿，架构仅保留已审核文件与 `当前架构.md`。

### 2.6 异常与重试 ✅ 已完成

1. `ModelChatService` + `@SentinelResource("aiModelChat")` 包装模型调用；Nacos `book.ai.sentinel.max-retries` / `retry-interval-ms`。
2. `POST /task/{id}/retry`：失败任务按原 `input_params` 重新提交。

**本切片验收**：多候选打分可对比转正；操作日志落盘；导出可选仅已审核；失败任务可重试；模型调用走 Sentinel 降级。

## 阶段 3：创作工作台前端（面向写手）

**目标**：脱离临时借用的 `book-gen` 管理页，做一个独立的、面向最终写手用户的创作前端。

**前置条件**：阶段2接口稳定。

1. 技术选型：Vue3 + Vite + Pinia（区别于 `book-ui` 的 Vue2 技术栈，独立仓库/独立目录 `book-workstation`，通过网关或独立域名接入，登录态复用 `book-auth` 的 JWT）。
2. 页面清单：项目列表 → 项目详情（资料上传/架构查看编辑）→ 大纲树/章节列表 → 章节编辑器（正文 + AI 优化对比面板，参考阶段2的多候选打分结果做并排对比 UI）→ 审核面板（通过/驳回 + 意见）→ 导出下载入口。
3. 生成类操作统一走"提交任务 → 显示进度条（SSE）→ 完成后刷新"的交互模式。
4. 知识库文件浏览器（可选）：`GET /project/{id}/kb/tree` + `GET /project/{id}/kb/file?path=`，用简单的树形控件 + Markdown 预览，方便用户直接查看 Obsidian 目录结构。

**验收标准**：非技术背景的用户能独立完成"创建项目 → 上传 → 审核架构 → 生成并审核若干章 → 下载"全流程，无需查看接口文档。

## 阶段 4：长篇连贯性增强（向量检索 RAG）

**目标**：解决长篇创作中人设漂移、伏笔遗忘问题。

**前置条件**：已积累一定量的真实项目数据（至少几个项目、每个项目 10+ 章节），否则没有效果评估的基础。

1. 引入向量库：优先用 pgvector（团队已有 MySQL，若不想额外引入 PostgreSQL，可评估 Milvus 或 MySQL 自带向量能力，具体选型在真正做这一阶段时结合当时生态成熟度重新调研，不在此提前锁死）。
2. 新增 `KnowledgeBaseIndexer`：对 `01-全局架构/当前架构.md`、`02-章节内容/*.md` 做分块 + embedding，写入向量库，关联 `projectId`/`chunkSource`。
3. 章节生成前，新增一步"检索相关上下文"：以本章大纲/关键人物为 query 做向量检索，取 top-K 相关片段拼入 prompt 上下文，替代/补充当前"整份架构全量塞入 prompt"的做法（长篇场景下架构+已写章节太长塞不进上下文窗口）。
4. 效果验证：人工抽查生成章节，对比引入 RAG 前后人设一致性、伏笔呼应情况。

**验收标准**：能明显减少人工审核中"人设矛盾/伏笔遗忘"类驳回比例（需在阶段2先积累驳回原因分类数据作为基线）。

## 阶段 5：多租户、计费与成本控制

**目标**：从"能跑"走向"能对外运营"。

1. 用量限额：基于 `ai_usage_log` 统计每用户/每项目 token 消耗，`book.novel` 新增用户套餐配置（免费额度、超额提示/拦截）。
2. 成本看板：管理端页面展示模型调用成本、按用户/时间维度的消耗趋势（复用 `book-ui` 后台管理，新增报表页）。
3. 计费对接：视产品阶段决定接入第三方支付还是先做手动充值记账，不在技术方案里提前假设具体支付渠道。
4. 多租户隔离检查：全量接口过一遍，确认所有查询都带上 `user_id`/项目归属校验（防止越权访问他人项目）。

**验收标准**：普通用户无法通过接口访问/操作不属于自己的项目；超额后有明确提示且不会无限调用模型导致成本失控。

## 阶段 6：质量加固（测试 / 监控 / 安全）

**目标**：达到可以稳定对外提供服务的工程质量水位。

1. **测试**：`book-novel`/`book-ai` 核心 Service 补单元测试（重点：`KnowledgeBaseStorage` 路径安全、`PromptTemplateService` 渲染正确性、状态机流转）；关键流程补集成测试（创建项目→生成→审核→导出）。
2. **监控**：`book-visual-monitor`（Spring Boot Admin）接入 `book-novel`/`book-ai` 新服务；关键业务指标（任务成功率、平均生成耗时、模型调用失败率）埋点，可先用日志+简单统计接口，量大后再接 Prometheus/Grafana。
3. **安全审计**：
   - `ai_model_config.api_key` 确认已加密存储、日志不打印明文 Key。
   - 文件路径穿越、越权访问项目、上传文件类型/大小限制逐项检查。
   - 触发一次 `security-review` 子代理（Cursor 内置技能）对本阶段代码做安全审查。
4. **性能**：模拟并发生成请求，验证线程池/数据库连接池配置在预期并发量下不打满；长文本存储（MEDIUMTEXT/LONGTEXT）读写性能验证。

**验收标准**：核心链路测试覆盖到位；一次完整的安全审查无高危问题遗留；关键指标可观测。

## 阶段 7：部署与上线交付

**目标**：完成生产环境部署，正式交付。

1. `docker-compose.yml` 新增 `book-novel`/`book-ai` 服务定义，`book.novel.kb.root-path` 挂载生产磁盘路径（如 `/data/book/kb`，用 Docker volume 持久化，避免容器重建丢数据）。
2. Nacos 生产命名空间配置核对：模型 API Key 通过环境变量/密钥管理注入，不落库不落配置文件明文。
3. 数据库迁移脚本核对：`sql/` 目录下所有新增建表脚本按顺序在生产库执行一遍，确认无遗漏。
4. 灰度/回滚方案：先在小范围用户验证，确认稳定后再全量开放；保留导出 zip 功能作为"最坏情况下用户仍可拿到自己数据"的兜底。

**验收标准**：生产环境完成一次真实用户从注册到导出成品的完整流程验证；具备基本的故障恢复能力（服务重启不丢数据、模型异常有告警）。

## 附录 B：主要风险与开放问题

- DeepSeek/豆包 API 的限流、计费规则、长上下文支持情况需在阶段1联调时实测确认，可能影响阶段4的分块策略。
- 向量库选型（pgvector vs Milvus vs 其他）留到阶段4临近开始时再定，避免过早引入 PostgreSQL 增加阶段1-3的运维复杂度。
- SSE 在生产网关/反向代理下需确认不被中间层缓冲（Nginx 需关闭 `proxy_buffering`），部署阶段需专项验证。
- 多租户计费方案涉及产品/商业决策（免费额度、定价），非纯技术问题，阶段5启动前需先与产品侧对齐。
